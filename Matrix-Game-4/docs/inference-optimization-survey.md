## 1. 成本画像

### 1.1 实测分解（`kernels` 运行时，144 帧稳态，TAEHV，SDPA）

| 配置 | 块耗时 | encode | denoise | clean_KV | decode | FPS | 峰值显存 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 480×864 | 362 ms | 12.8 | 165.3 | **165.2** | 18.5 | 10.45 | 12.84 GB |
| 352×640 | 242 ms | 9.3 | 92.3 | 89.8 | 50.4 | 15.68 | 11.43 GB |
| 288×512 | 188 ms | 8.0 | 83.7 | 81.7 | 14.8 | 20.20 | 10.79 GB |

### 1.2 单次前向的内部构成（480×864）

| 项 | 耗时 | 占比 | 说明 |
| --- | --- | --- | --- |
| 自注意力 | 90.6 ms | 55% | 30 层 × 3.02 ms，405 查询 × 8505 key（21 帧窗口） |
| GEMM / FFN / 调制 | ~75 ms | 45% | FFN 单层 1.23 ms（实测 57.8 TFLOPS） |

### 1.3 三个结构性事实

1. **每块跑两次前向**：`denoise` 产出去噪结果，`clean`（t=0、`drop_control=True`）把它写回 KV。
   合计占块耗时 **91%**。
2. **注意力随 KV 长度线性增长**：窗口是运行时参数 `set_attention_window(generator, 21, 1)`。
3. **分辨率是二次惩罚**：token 数 ∝ 像素，注意力 ∝ token²。
   480×864 → 405 token；720×1280 → 920 token（注意力约 5.2 倍）。

### 1.4 已经拿到的收益（作为基线，不再重复计）

| 手段 | 收益 | 状态 |
| --- | --- | --- |
| `native` → `kernels` 运行时 | **+66%** | ✅ 默认 |
| hipGraph（`cudagraph` / `ring-graph`） | +5% | ✅ 已验证，收益有限 |
| 分辨率下调（480p → 288p） | +93% | ✅ 已验证，画质代价 |
| 抓屏 Pillow → mss（交互链路） | 延迟 1519 → 258 ms | ✅ 已验证 |

## 2. 指标定义

后续每项实验都必须同时报告以下指标，**缺一不可**：

| 指标 | 定义 | 采集方式 |
| --- | --- | --- |
| `chunk_ms` | 一块（1 latent = 4 像素帧）的端到端耗时 | `perf_harness.py` 内计时 |
| `model_fps` | 4 / `chunk_s` | 同上 |
| `lag_ms` | 最新输入帧 → 预览显示的时长 | `play_rendered.py` 状态栏 |
| `vram_gb` / `commit_gb` | 峰值显存 / 提交内存 | harness 护栏与采样 |
| **质量分** | 见 §2.1 | 抽帧 + 指标脚本 |
| 崩溃次数 | 进程级 `0xC0000005` / 机器级重启 | 人工记录 |

### 2.1 质量验收口径

我们没有高保真 GT（自有采集只有低模），因此采用**相对基线**的三段式验收：

1. **保真度**：与"全量 clean + 21 帧窗口"的基线渲染逐帧比对，报告 LPIPS / SSIM 均值与最差 5%。
2. **时序稳定性**：`flicker = std_t( mean_abs(Δframe_t − Δproxy_t) )`
   —— 输出帧间变化应当跟随代理（低模）帧间变化；该项突增即说明 KV 漂移或窗口过短。
3. **人眼抽查**：每个配置抽 3 帧（第 8 / 40 / 120 块附近），并排比对。**画质崩坏必须肉眼可见地确认**，不能只看数字。

> 经验阈值：LPIPS 均值劣化 < 5%、`flicker` 增幅 < 15%、人眼无可见崩坏 → 通过。

## 3. 实验协议

### 3.1 单变量原则

每次只改一个候选的**一个参数**，其余固定为当前推荐配置
（`--preset rocm` + 480×864 或 288×512 + `--frames 144`）。

### 3.2 标准命令

```powershell
cd Matrix-Game-4
$env:TMP='D:\work\Matrix-Game\.tmp'; $env:TEMP=$env:TMP
# 离线、无并发抓屏：当前机器最稳的形态
..\.venv-rocm\Scripts\python.exe scripts\perf_harness.py `
  --input ..\captures\long-144f.mp4 --resources resources --preset rocm `
  --frames 144 --max-commit-gb 40 --matrix <配置名>
```

### 3.3 记录模板（写入 `inference-optimization-matrix.md`）

```
| 日期 | 候选 | 参数 | 分辨率 | chunk_ms | FPS | 显存 | LPIPS vs 基线 | flicker | 结论 |
```

### 3.4 环境约束

- 当前机器存在两类稳定性问题（见 plan §18）：**只做离线渲染实验**，不加并发抓屏。
- 每次实验前确认提交内存 < 20 GB；崩溃后等进程退出、内存归还再继续。
- 质量对比必须与**同一次会话**内产生的基线对比，避免跨会话随机种子差异。

## 4. 候选方案

优先级按「收益 ÷ 风险」排序：**O1 → O2 → O3 → O4 → O7 → O8 → O5 → O6**。

---

### O1. fp16 替代 bf16 —— ❌ 已实测否决

| 项 | 内容 |
| --- | --- |
| **原理** | 本机实测 GEMM：bf16 82.9 TFLOPS vs **fp16 92.3 TFLOPS（+11%）** |
| **实测结果** | 480p：bf16 350.4 ms / 10.81 FPS → fp16 399.6 ms / 9.48 FPS；288p 同样无收益 |
| **逐阶段（480p, p50）** | denoise 173.7 → 174.7；clean 170.6 → 172.3；decode 6.4 → 2.1 |
| **为什么无效** | 真实前向里注意力占 55%，且受 kernel 启动与访存支配，GEMM 峰值用不满，换精度不影响瓶颈 |
| **附带问题** | fp16 的 decode 出现个别数百毫秒停顿（p50 2.1 ms vs 均值 68.6 ms），交互下会卡顿 |
| **结论** | **否决**。画质无异常，但零收益且有偶发卡顿风险。 |

---

### O2. 流水线重叠 —— ❌ 已实测否决

| 项 | 内容 |
| --- | --- |
| **原理** | `decode` 与 `clean_kv` 无数据依赖，应可并行 |
| **实测结果** | 480p 350.6 ms（基线 350.4）；288p 182.0 ms（基线 180.9）——**净收益≈0** |
| **发生了什么** | decode 确实被隐藏（15.9 → 1.7 ms），但 clean_kv 同步变慢（159.7 → 173.5 ms），省下的时间被争用吃掉 |
| **数值一致性** | PSNR = inf，SSIM = 1.000000（完全逐位一致） |
| **结论** | **否决并回退代码**。这一结果证明 **推理时 GPU 已饱和**。 |

---

### 重要推论：GPU 已饱和

批次 1 两个候选都是负结果，但共同指向一个关键事实：**这台 GPU 在 DiT 前向期间没有空闲算力**。

| 类别 | 预期 | 依据 |
| --- | --- | --- |
| 调度 / 并行类（多 stream、更细流水、异步发布） | **≈0** | O2 实测 |
| 精度类（fp16） | **≈0** | O1 实测 |
| **减少工作量**（O3 缩窗口、O4 跳过 clean） | **接近线性** | 前向是瓶颈，去掉的 FFN/attention 直接省时间 |
| 提高单次效率（O5 split-K、O6 token 压缩） | 有收益但受限于平台/风险 | 微分基准显示注意力还有优化空间 |

因此**后续批次应集中投入 O3 与 O4**，不再在调度上花时间。

---

### O3. KV 窗口收缩 —— ✅ 已实测，部分采纳

| 项 | 内容 |
| --- | --- |
| **原理** | 自注意力成本 ∝ KV 长度。窗口 21 帧是**推理时的运行时选择**（训练用 81 帧双向窗口）。 |
| **实测（480p）** | w16 11.69 FPS（+8%）；**w12 12.35 FPS（+14%）**；w8 14.00 FPS（+29%，画面略软） |
| **实测（288p）** | w16 21.07 FPS（+1%）；**w12 23.12 FPS（+11%）**；w8 23.90 FPS（+15%） |
| **附带收益** | 显存随窗口下降：480p 12.84 → 11.57 GB（w12） |
| **端到端** | 48 帧 @480×864 渲染 7.23 s → 5.04 s（`--window 12`） |
| **代码** | `--window` CLI（`scenes.py`），贯通 `loader.stream` / `offline` / harness |
| **结论** | **w12 为推荐值**；w8 收益递减且偏软；w16 在 288p 无意义 |
| **风险** | 长程记忆：w12 ≈ 48 帧（2 秒）的上下文。本测试片段未暴露问题，**长回访场景仍需验证** |

**踩坑记录**：同进程内切换窗口（21→16）会产出纯噪声且不报错，根因未定位。
已加 `looks_degenerate` 自动检测；**窗口扫描必须每窗口一个独立进程**。

---

### O4. clean-KV 降频与运动自适应 —— ✅ 已实测，固定降频采纳

| 项 | 内容 |
| --- | --- |
| **原理** | 蒸馏训练时学生看到干净 GT KV，推理每块重算一次。但 KV 漂移速度取决于画面变化速度，而 control latent 的帧间差异是现成的运动度量。 |
| **实测（480p）** | 每 2 块 13.43 FPS（+24%）；**每 4 块 15.48 FPS（+42%）**；每 8 块 17.04 FPS（+57%，**画质退化**） |
| **实测（288p）** | **每 4 块 28.97 FPS（+39%）**（基线 20.84） |
| **自适应** | θ=0.35 → 14.35 FPS（+32%）；θ=0.5 → 14.47（+33%）；θ=0.2 不触发（运动中位数就是 0.25） |
| **代码** | `--clean-every` / `--clean-adaptive` / `--clean-threshold` / `--clean-max-gap` |
| **结论** | **`--clean-every 4` 为推荐上限**；c8 明显退化；自适应需按场景标定阈值，收益不优于固定 c4 |

**方法论教训（重要）**：用"逐帧 PSNR 对比基线"验收自回归模型会误判。
c4 与基线的 PSNR 在第 6 帧（首次跳过 clean）就从 40 dB 掉到 18 dB，之后稳定在 15.5 dB，
但三行并排（proxy / 基线 / c4）显示 c4 的几何完全跟随代理，只是**色调外观分叉**。
**正确判据是"是否跟随代理几何"**，不是与基线逐像素一致。
而 c8 在同一张对比图里第 44 帧角色被大片黑色物体遮挡、走廊结构偏移——这才是真实退化。

### O5. 注意力分块（split-K / flash-decoding）

| 项 | 内容 |
| --- | --- |
| **原理** | 查询只有 405 token，KV 有 8505——典型"短查询 × 长 KV"，并行度不足。沿 KV 维切分、各分块算部分 softmax 再加权合并，可把 SM 喂满。 |
| **代码落点** | 需替换 SDPA 调用点；仓库的 `ring-fused` 运行时已用 Triton 实现类似思路。 |
| **预期收益** | 注意力 3.02 → 约 2.0–2.4 ms/层，480p 块耗时 -10%~-13% |
| **风险** | 数值误差（分块 softmax 的精度）、实现复杂度高 |
| **工作量** | 5+ 天，且**Windows 上无 Triton，无法落地** |
| **依赖** | **Linux/WSL2**（结论：暂缓，列入"换平台后再做"） |

---

### O6. 训练-free token 压缩（ToMe 式）

| 项 | 内容 |
| --- | --- |
| **原理** | KV 中大量 token 是背景（天空、地面、重复墙面）。按相似度合并 token 可把 KV 压到 ~70%。 |
| **预期收益** | 注意力 -25%，480p 块耗时 -14% |
| **风险** | 模型未见过合并后的 KV，几何细节易糊；误差沿时间累积 |
| **工作量** | 3–5 天，收益/风险比最差 |
| **结论** | **最后手段**，仅当 O1–O4 用尽后考虑 |

---

### O7. 后处理超分（提升观感分辨率）

| 项 | 内容 |
| --- | --- |
| **原理** | 渲染分辨率与显示分辨率解耦：288×512 渲染 → 轻量 SR 网络放大到 1024×576/1280×720 显示。 |
| **代码落点** | 与 `decode` 之后、发布之前，独立于 DiT；`play_rendered.py` 的显示路径或渲染服务输出端。 |
| **预期收益** | 288p 的 188 ms 块耗时 + SR ~20 ms/块 → 观感分辨率接近 480p 原生，代价 +11% |
| **风险** | SR 幻觉细节与模型输出不一致；快速运动时出现拖影 |
| **候选模型** | Real-ESRGAN 轻量版 / SPAN / Anime4K（后者零依赖、CPU 亦可） |
| **工作量** | 1–2 天 |
| **依赖** | 无（但需选定 SR 模型并量化耗时） |

---

### O8. 帧插值（提升观感流畅度）

| 项 | 内容 |
| --- | --- |
| **原理** | 模型 15 FPS，显示 60 FPS：用光流插帧（RIFE / FILM）在相邻输出帧之间生成中间帧。**延迟不变，观感流畅度翻倍**。 |
| **代码落点** | 渲染服务的输出端（与 `play_rendered.py` 的显示循环解耦） |
| **预期收益** | 观感帧率 4× （15 → 60），代价 ~3–5 ms/插值帧（512p） |
| **风险** | 插值伪影（快速运动、遮挡边界）；额外 1 帧延迟 |
| **工作量** | 1–2 天 |
| **依赖** | 无 |

## 6. 明确不可行

| 手段 | 原因 |
| --- | --- |
| **真正的 720p 实时** | 720×1280 的 token 数是 480p 的 2.27 倍，注意力 ×5.2、GEMM ×2.3 → 每块 700–900 ms（4–5 FPS）。这是二次复杂度决定的上界，不是工程问题。 |
| **FP8 推理** | gfx1100（RDNA3）无 FP8 硬件单元；INT8 仅 DP4A 级吞吐。 |
| **Triton 融合内核** | Windows 上无 Triton，`ring-fused` 不可用。差距约 10–15%，需换 Linux/WSL2。 |
| **权重量化到 INT4** | 需要校准与可能的精度补偿，且本机无对应 GEMM 加速路径，收益接近零。 |
